# 프로젝트 원칙 — 작업의 기준점

star.byb.kr 플레이트 솔버를 만들 때 모든 결정의 기준으로 삼는 원칙이다.
방향이 헷갈리거나 원칙끼리 부딪히면 이 문서로 돌아온다. 새 원칙이 생기면 번호를 이어서 추가한다.

(2026-10-19 정리. 번호는 처음 정리한 순서를 그대로 두어, "N번 원칙"으로 부를 수 있게 한다.)

---

## A. 이 프로젝트가 무엇인가

### 1. 직접 만드는 플레이트 솔버
- **"내가 직접 만든다"는 데에 가장 큰 의미가 있다.** Astrometry.net보다 성능이 낮아도 감수한다.
- 그래서 Astrometry.net의 인덱스 파일이나 라이브러리, 외부 풀이 API를 가져다 쓰지 않는다.
  논문의 아이디어(geometric hashing 등)를 참고하는 건 괜찮지만, 구현은 직접 한다.
- 카탈로그(BSC5 등)처럼 공개된 *데이터*는 쓴다.

### 2. 그래도 성능은 좋을수록 좋다
- 직접 만든다는 이유로 성능을 포기하지는 않는다. 더 나아질 수 있으면 계속 개선한다.
- 개선은 반드시 측정해서 확인한다 (→ 12번 단계별 테스트·벤치마크).

### 8. 응용으로 이어진다
- 여기서 만든 기술(천구 ↔ 사진 좌표 변환, 별자리 투영, 합성 밤하늘 생성 등)은
  별자리 그리기 게임, 별자리 맞추기 게임 같은 응용의 바탕이 된다.
- 그래서 핵심 로직은 특정 화면에 묶지 않고, 따로 떼어 다시 쓸 수 있게 만든다 (→ 10번).

---

## B. 누가, 어떤 사진으로 쓰는가

### 4. 일반인이 아무렇게나 찍은 사진에도 강건하게
- 대상: 다양한 화각, 저화질, 흔들린 사진, 지상 물체(건물·산·조명)가 함께 찍힌 사진, 구름이 섞인 사진.
- Astrometry.net이 약한 부분이고, 이 프로젝트가 차별점을 가질 수 있는 부분이다.
- 기본 전략: **하늘이 아닌 요소(지면·건물·구름·조명)를 가려내고, 남은 별로 풀고 확인한다.**

### 5. 최대한 자동으로, 필요하면 사람이 돕는다
- 자동으로 찾는 것이 기본 목표다.
- 지금 자동화가 어려운 단계(예: 4번의 "하늘이 아닌 요소" 가려내기)는
  사람이 마커를 지우거나 추가하고, 영역을 고르는 식으로 협업한다.
- 관련 기술이 발전하면 그 협업 단계를 하나씩 자동으로 바꾼다.
- **풀지 못하면 정직하게 "확신 못 함"이라고 한다.** 틀린 해를 정답처럼 내놓지 않는다.
- 특정 사진에 맞춘 처리를 코드에 박아 두지 않는다. 모든 사진이 같은 흐름을 탄다.

### 9. 일반인이 쓸 수 있을 만큼 빠르게
- 빠를수록 좋다. **목표는 10초 안쪽, 상한은 1분 정도.**
- 몇 초 이상 걸리는 단계에는 로딩 UI(진행 상황)를 보여 준다.
- 시간은 단계별로 측정해서 어디가 느린지 안다 (DB 로딩, 검출, 매칭, 검증).

### 13. 핵심이 잘 되면, UX를 생각한 서비스로
- 핵심 기능(풀이)이 안정되면 일반인이 쓰기 편한 서비스로 다듬는다.
- 순서: 핵심 기능의 정확도·속도 → 협업 도구의 사용성 → 서비스 전체의 UX.

## C. 어디서, 얼마의 비용으로 돌리는가

### 6. 호스팅 비용은 적게
- 서버에 올리더라도 비용(특히 다운로드 용량)이 적어야 한다.
- 카탈로그·해시 DB 크기를 늘릴 때는 그만큼 내려받는 용량이 늘어난다는 걸 함께 따진다.
  (`CLAUDE.md`의 "별 등급별 성능 분석" 참고: V≤4.5 약 6MB, V≤5.0 약 63MB)
- 줄이는 방법: binary 형식, 압축, 필요한 부분만 내려받기, 브라우저 캐시.

### 7. 로직은 되도록 프론트에서
- 풀이 로직은 브라우저(Web Worker)에서 돌린다. 호스팅 서버는 정적 파일만 내려준다.
- 무거운 계산은 Worker로 보내서 화면이 멈추지 않게 한다.
- 6번과 같이 본다: 프론트에서 돌리려면 DB를 내려받아야 하므로, **DB 크기가 곧 비용이자 첫 로딩 시간**이다.

## D. 어떻게 만드는가

### 10. 기술적 완성도를 챙긴다
- 테스트, 로직의 정확성, 코드 품질, 변수명, 코드 재사용, 성능 최적화를 고루 챙긴다.
- 핵심 로직은 순수 함수(`*Core.ts`)로 두고, Worker·React hook은 얇은 감싸개로 둔다.
  그래야 Node 테스트, 브라우저, 다른 응용(8번)이 같은 코드를 쓴다.
- 같은 계산(투영, 좌표 변환 등)을 여러 곳에 따로 구현하지 않는다. 한쪽만 고쳐져 어긋나는 버그가 실제로 있었다
  (`useSkyOverlay`만 카메라 뒤쪽 별을 거르지 않았던 사례).

### 12. 단계별로 나누고, 테스트로 보강하며 완성한다
- 플레이트 솔빙을 단계로 나눈다: **검출 → 정리(하늘 아닌 요소 제외) → 매칭 → 검증 → 투영·표시**.
- 각 단계를 따로 테스트하고, 전체도 함께 테스트한다.
  - 합성 데이터(정답을 아는 사진)로 단계별 정답률을 측정한다.
  - 실제 샘플 사진의 정답(`sampleAnswers.ts`, `data/search/`)으로 확인한다.
- 개선할 때는 숫자로 전후를 비교한다. 테스트는 매번 같은 결과가 나와야 한다.
- 변경 → lint → 테스트 → 커밋을 작은 단위로 반복한다.

## E. 발표와 기록

### 3. 각 단계를 보기 쉽게 — 사내 개발자 세미나용
- 플레이트 솔버의 각 단계를 눈으로 보여 주는 화면을 만든다.
- 발표 자료는 웹으로 구성하고, 중간에 iframe으로 데모 페이지를 연결해 시연한다
  (V2 발표는 `src/app/demo/*`를 iframe으로 띄웠다. 지금은 `/embed/<이름>`으로 찾는 원리 데모를 띄운다).
- 그래서 데모 페이지는 iframe 안에서 단독으로 잘 동작해야 한다.

### 11. 진행 과정을 문서로 남긴다
- 무엇을 시도했고, 무엇을 발견했고, 왜 그렇게 결정했는지 기록한다. 발표 자료로 그대로 쓴다.
- 기록 위치:
  - `docs/experiments-journey.md` — 시도·발견·교훈 (문제 → 시도 → 결과 → 교훈 순서)
  - `docs/algorithm-comparison.md`, `docs/benchmark-results.json` — 알고리즘 비교 수치
  - `docs/*-todo.md` — 미뤄 둔 과제
  - 이 문서 — 원칙

## 원칙끼리 부딪힐 때

| 상황 | 기준 |
|---|---|
| 성능 vs 직접 구현 (1·2) | 직접 구현이 먼저. 외부 솔버를 쓰면 성능이 올라도 하지 않는다 |
| 정확도 vs DB 크기·속도 (2·6·9) | 첫 로딩 시간과 내려받는 용량까지 포함해 10초 목표 안에서 고른다 |
| 자동화 vs 정확도 (4·5) | 자동으로 틀리느니 사람에게 묻는다. 확신 못 하면 확신 못 한다고 한다 |
| 새 기능 vs 핵심 완성 (8·13 vs 12) | 핵심 풀이 단계가 테스트로 단단해진 다음에 응용·UX로 넓힌다 |
