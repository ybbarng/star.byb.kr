# 다운로드 용량 최적화 — 8MB에서 0.68MB로

> 발표용 정리. 시도·발견의 원본 기록은 `experiments-journey.md` 27·28장, 설계 배경은 `database-design.md` 5장.

## 한 줄 요약

플레이트 솔버를 열어 사진 한 장을 풀 때까지 받는 양(압축 전송 기준)을 **약 8MB → 약 0.68MB**(1/12)로 줄였다.
정확도는 그대로다 (회귀 테스트 277개 통과, 실제 사진 회귀 포함).

핵심은 세 가지였다.
1. **받지 말고 만들자**: 패턴 DB는 "재료(별 위치) + 규칙"만 있으면 브라우저가 0.2초 만에 똑같이 만든다.
2. **쓰는 것만 받자**: OpenCV 11MB 중 쓰던 기능은 회색조·흐리기·빼기뿐이었다. 글꼴 2MB 중 화면에 쓰는 글자는 일부뿐이다.
3. **어림 말고 재자**: 실제로 재 보니 가장 큰 다운로드는 DB도 코드도 아닌 **글꼴**이었다.

## 프로젝트 원칙과의 관계

`project-principles.md`의 "프론트에서 실행·저비용". 풀이를 서버에 두면 받는 양은 0이지만 서버 비용이 든다.
그래서 "브라우저에서 돌리되, 받는 양은 일반 웹페이지 수준으로"가 목표였다.

## 측정 방법

- **받는 양**: `next build` → `next start`로 프로덕션 서버를 띄우고, 브라우저에서 플레이트 솔버를 열어 북두칠성 샘플을 풀 때까지
  Resource Timing의 `encodedBodySize`(압축 전송 크기)를 종류별로 더했다. 샘플 사진 자체는 뺐다.
- **만드는 시간·메모리**: node에서 단계별 시간과 힙을 쟀다 (핸드폰은 몇 배 느릴 수 있다).
- **정확도**: 매 단계 `npm test`(합성 + 실제 사진 회귀). 브라우저에서도 북두칠성·사이판 샘플을 직접 풀어 봤다.

## 전후 비교 (플레이트 솔버, 압축 전송)

| 받는 것 | 처음 | 지금 | 어떻게 |
|---|---:|---:|---|
| OpenCV.js (별 찾기) | 3.86MB | 0 | 순수 JS로 옮김 (27장) |
| 패턴 DB (quad 해시) | 1.46MB* | 0 | 받지 않고 Worker가 만듦 (28장) |
| 글꼴 (Pretendard) | 2.05MB | 0.31MB | 동적 부분 집합 |
| mathjs (전역 스크립트) | 0.19MB | 0 | 쓰는 곳이 없어 제거 |
| 별 카탈로그 | 0.09MB | 0.04MB | 쓰는 칸만, 좌표 8자리 |
| 앱 코드 (JS·CSS) | 약 0.3MB | 약 0.34MB | 카탈로그가 코드에 실림 |
| **합계** | **약 8MB** | **약 0.68MB** | |

\* 패턴 DB는 원래 JSON(10.8MB, 압축 약 3.5MB)이었고, 같은 날 이진 형식(2.04MB, 압축 1.46MB)으로 한 번 줄였다가 결국 받지 않게 됐다.

게임 페이지(예: SkyGuessr)는 약 0.68MB (JS 0.22·글꼴 0.39·CSS 0.04). 게임은 원래 패턴 DB·OpenCV를 받지 않았지만,
글꼴(2.05MB → 0.39MB)과 mathjs, 별 카탈로그 다이어트로 함께 줄었다.

## 단계별 이야기

### 1. OpenCV 빼기 (−3.86MB)

- **발견**: 11MB WASM 중 별 찾기가 쓰는 기능은 `cvtColor`(회색조), `GaussianBlur`(흐리기), `subtract`(빼기), `meanStdDev`(평균·표준편차)뿐.
- **한 일**: 순수 JS로 옮기고 Web Worker에서 돌린다. 51×51 가우시안은 **상자 흐림 세 번**으로 흉내 낸다
  (반지름과 상관없이 픽셀당 덧셈 몇 번 → 1,200만 화소 사진도 1~2초).
- **덤**: 브라우저와 테스트가 처음으로 **같은 별 찾기 코드**를 쓴다. 예전에는 테스트(sharp)와 브라우저(OpenCV)가
  흐리는 세기도, 흑백 변환 가중치도 달라서 "테스트 통과 = 브라우저에서 풀림"이 보장되지 않았다.
- **함정**: 바꾸고 나니 실제 사진 48개 중 1개(사이판)가 실패했다. 흐림 값을 맞추는 대신 원인을 따라가 보니,
  "한 줄로 늘어선 가짜 검출" 판정이 간격 9~12배도 정수배로 인정하는 허점이 있었다 → 배수 4배까지만 인정. (27장)

### 2. 패턴 DB를 받지 않고 만들기 (−1.46MB)

- **발견**: quad 해시 DB는 "별 위치 + 규칙(하늘을 192칸으로, 칸마다 10° 안에 모인 별 네 개)"으로 언제든 다시 만들어진다.
- **한 일**: Worker가 페이지를 열 때 직접 만든다 (`quadDatabase.ts`, node 0.12~0.2초).
  예전 파일과 비교해 **quad 82,703개가 정확히 같다**는 것을 확인했다 (해시 차이 6e-8, float32 반올림).
- **덤**: 이웃 칸이 겹쳐 두 번 들어 있던 quad 2,259개(2.7%)가 빠졌다. 배포 때 DB 파일을 따로 올릴 필요도 없어졌다.

### 3. 모든 페이지가 받던 것 정리 (−2.0MB 안팎)

- **mathjs**: 루트 레이아웃이 모든 페이지에서 화면 그리기 전에 CDN의 mathjs 전체(압축 186KB)를 받았지만,
  전역 `math`를 쓰는 코드가 없었다 (옛 코드의 흔적). 풀이 경로의 mathjs도 3×3 행렬 계산뿐이라 순수 JS로 옮겼다.
- **글꼴**: Pretendard 가변 글꼴 통짜 파일(한글 1만 1천여 자, 2.05MB)을 모든 페이지가 받았다.
  공식 **동적 부분 집합**(92조각, `unicode-range`)으로 바꿔 화면에 쓰인 글자가 든 조각만 받는다 → 0.31~0.39MB.

### 4. 별 카탈로그 다이어트 (−50KB, 게임 포함)

- 앱이 쓰지 않는 칸(문자열 적경·적위, 별자리 약어 등), 소수 16자리 좌표, 들여쓰기를 뺐다: 399KB → 138KB (압축 93 → 41KB).
- **함정**: 좌표를 8자리로 줄이자 테스트 하나가 0.003° 오차로 실패했다. 실제 방향 차이는 0.002″인데,
  벡터 길이가 1에서 1e-8 벗어난 것을 `acos`가 1 근처에서 크게 부풀린 것이었다 → 방향끼리 비교하도록 테스트를 고침.

## 받는 대신 만드는 비용 (풀이 준비, node)

| 단계 | 처음 | 지금 |
|---|---:|---:|
| 패턴 DB | 받기 1.46MB + 풀기 7ms | 만들기 0.12~0.2초 |
| 검색 트리(4D KD-tree) | 0.31초 | 0.035초 (타입 배열 전용 구현) |
| 삼각형 인덱스 (113만 개) | 0.53초, 메모리가 259MB까지 | 0.55초, 66MB (타입 배열) |
| 합계 | 약 0.85초 + 1.46MB 다운로드 | **약 0.8초, 다운로드 없음** |

사진을 고르는 동안 Worker가 미리 해 두므로 사용자가 기다리는 시간은 거의 없다.

## 계획과 실제

2026년 초 `database-design.md`의 전망은 "OpenCV 제거 + 이진 형식 + 셀당 상한 → 약 1.5MB"였다.
실제로는 그보다 작은 **0.68MB**가 됐는데, 계획에 없던 두 가지 덕분이다.
- 이진 형식으로 줄이는 대신 **아예 받지 않기** (계획은 "더 작게 받기"였다)
- 계획 목록에 없던 **글꼴과 전역 mathjs** (재 보기 전에는 몰랐다)

## 발표용 메시지

1. **"받을 것은 규칙과 재료뿐이었다"** — DB를 줄이는 고민보다, DB가 왜 필요한지를 다시 물었다.
2. **"재 보면 의외의 곳이 크다"** — 가장 큰 다운로드는 글꼴이었다.
3. **"도구를 바꾸면 그 위의 허점이 드러난다"** — OpenCV를 빼자 별 찾기 위의 휴리스틱 허점이 보였고,
   덤으로 테스트와 브라우저가 같은 코드를 쓰게 됐다.

### 슬라이드 구성 제안

1. 문제: "별 사진 한 장 풀려고 8MB?" — 처음 받는 양 막대그래프 (OpenCV·글꼴·DB가 대부분)
2. 받지 말고 만들자: 패턴 DB = 별 위치 + 규칙, 0.2초, 82,703개 똑같음
3. 쓰는 것만 받자: OpenCV(기능 4개), 글꼴(쓰인 글자 조각만)
4. 재 보니 1등은 글꼴: 측정 방법(Resource Timing)과 함께
5. 결과: 8MB → 0.68MB 막대그래프, 정확도 그대로(테스트 277개)

## 더 줄일 수 있는 것 (선택)

- **글꼴**: 가변 글꼴 대신 고정 굵기 두 개(보통·굵게)의 부분 집합 — 30~50% 더 줄 것으로 예상 (재 보지 않음).
  화면에서 쓰는 굵기 단계가 줄어든다.
- **별을 더 늘릴 때**(5.5등급 이상): quad가 C(k,4)로 폭발한다. 받는 양은 늘지 않지만 만드는 시간·메모리가 문제 →
  칸마다 별 수 상한, HEALPix nside 조정.
