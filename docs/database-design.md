# Plate Solver 데이터베이스 설계

## 개요

Plate Solver는 밤하늘 사진에서 별자리를 식별하기 위해, 미리 계산된 별 패턴 데이터베이스를 사용한다. 이 문서는 데이터베이스의 구조, 생성 과정, 그리고 설계 결정의 근거를 설명한다.

## 파이프라인

데이터베이스 생성은 `build_database.sh`를 통해 4단계로 수행된다.

```
BSC5 카탈로그 (9,096별)
  → [1] reduceDatabase: 밝기 기준 필터링
  → [2] toVector: RA/Dec → 3D 단위벡터 변환
  → [3] createHashFromDatabase: HEALPix 셀 분할 → Quad 생성 → 해시 계산
  → [4] buildConstellations: 별자리 연결선 데이터 생성
```

## 1. 별 필터링

원본 BSC5(Bright Star Catalogue 5th edition) 카탈로그에는 9,096개의 별이 포함되어 있다. 이 중 밝기(겉보기 등급, V)가 일정 이하인 별만 사용한다.

### 등급별 규모

| 최대 등급 (V) | 별 수 | Quad 수 | DB 크기 |
|:---:|:---:|:---:|:---:|
| 4.0 | 518 | ~8K | ~1 MB |
| 4.5 | 904 | ~55K | ~6 MB |
| 5.0 | 1,630 | ~546K | ~66 MB |
| 5.5 | 2,900+ | 수백만 | 수백 MB |

등급 시스템에서 숫자가 작을수록 밝은 별이다. 현재는 **V <= 5.0 (1,625개, 중복 좌표 제거 후)** 을 사용한다.

### parseInt vs parseFloat 이슈

카탈로그의 V(등급) 값은 문자열(`"4.61"`)로 저장되어 있다. 초기 구현에서 `parseInt`를 사용했는데, `parseInt("4.61")` = 4 이므로 의도와 다르게 V < 5.0인 별까지 모두 통과시키고 있었다. `parseFloat`로 교체하여 정확한 필터링이 이루어지도록 수정하였다.

## 2. 천구 분할: HEALPix

### 분할 방식

천구를 균등하게 분할하기 위해 HEALPix(Hierarchical Equal Area isoLatitude Pixelisation)를 사용한다. `nside = 4`로 설정하면 천구가 **192개 셀**로 나뉘며, 각 셀은 약 15° x 15° 크기이다.

### 겹침(Overlap) 전략

각 셀 중심에서 **600 arcmin(10°) 반경** 내의 모든 별을 수집한다. 셀 자체 크기(~15°)보다 수집 반경(10°)이 크기 때문에, 인접 셀 사이에 약 5° 폭의 겹치는 영역이 생긴다.

```
셀 A 중심 ←── 15° ──→ 셀 B 중심
|←── 10° 반경 ──→|
              |←── 10° 반경 ──→|
              |← 5° 겹침 →|
```

이 겹침은 의도적인 설계이다.

**목적**: 사진 속 4개 별(quad)이 셀 경계에 걸쳐 있더라도, 적어도 하나의 셀에는 4개 별이 모두 포함되도록 보장한다. 겹침이 없으면 경계 근처의 별 패턴이 어떤 셀에도 완전히 포함되지 않아 매칭에 실패할 수 있다.

**중복 영향**: 겹침 영역에 있는 별은 여러 셀에 중복 포함되므로, 동일한 quad가 여러 셀에서 생성될 가능성이 있다. 그러나 실제로는 중복이 매우 적다.

| 항목 | 값 |
|:---|:---:|
| 전체 Quad 수 | 545,855 |
| 고유 Quad 수 | 543,307 |
| 중복 Quad 수 | 2,548 |
| 중복률 | 0.5% |

중복이 적은 이유: 겹침 영역에 **별** 1개가 포함될 확률은 상당하지만, quad를 구성하는 **4개 별 모두**가 동시에 겹침 영역에 있어야 중복이 발생한다. 이 확률은 개별 확률의 곱이므로 급격히 낮아진다.

### 셀당 별 분포 불균형

별은 천구에 균등하게 분포하지 않는다. 은하수 근처(은하면)에 밀집되어 있어 셀별 별 수 편차가 크다. Quad 수는 C(k, 4)로 계산되므로 별 수에 대해 4차적으로 증가한다.

| 셀당 별 수 | Quad 수 C(k,4) |
|:---:|:---:|
| 4 | 1 |
| 10 | 210 |
| 15 | 1,365 |
| 20 | 4,845 |
| 30 | 27,405 |
| 38 (최대, Cell 145) | 73,815 |

상위 10개 셀(전체의 5%)이 전체 quad의 약 62%를 생성한다. 이것이 DB 크기를 키우는 주된 원인이다.

## 3. Geometric Hashing

### Quad 정규화

4개 별로 구성된 사각형(quad)에서 기하학적 해시를 생성한다.

1. 4개 점 중 **가장 먼 2점**(A, B)을 찾는다
2. A → (0, 0), B → (1, 1)로 매핑하는 아핀 변환을 구성한다
3. 나머지 2점(C, D)을 변환하여 x좌표 순으로 정렬한다
4. 대칭성 제거: C.x + D.x > 1이면 (0.5, 0.5) 기준으로 반사한다
5. C와 D의 좌표 4개(Cx, Cy, Dx, Dy)가 **4D 해시**가 된다

### 불변성(Invariance)

이 해시는 회전, 스케일, 이동에 대해 불변이다. 같은 4개 별은 어디서 어떤 각도로 촬영하더라도 동일한 해시를 생성한다. 이를 통해 사진 속 별 패턴을 데이터베이스와 대조할 수 있다.

이 정규화 방식은 Astrometry.net 논문(Lang et al., 2010)에 기반한다.

### 4D 해시 분포 분석

정규화 알고리즘의 제약 조건으로 인해, 해시 값은 4D 공간에 완전히 균등하게 분포하지 않는다.

**각 차원의 통계**:

| 차원 | 범위 | 평균 | 표준편차 | 분포 특성 |
|:---:|:---:|:---:|:---:|:---|
| Cx | -0.41 ~ 0.50 | 0.02 | 0.20 | 0 근처 정규분포, 비교적 균등 |
| Cy | -0.32 ~ 1.41 | 0.62 | 0.39 | 완만한 피크, 비교적 균등 |
| Dx | -0.40 ~ 1.20 | 0.46 | 0.28 | **0.5 근처에 집중** (최대 12%) |
| Dy | -0.41 ~ 1.41 | 0.54 | 0.43 | 넓게 분포, 균등한 편 |

**4D 공간 점유율** (0.1 간격 격자 기준):
- 이론적 전체 셀 ~58K 중 18,629개 점유 (**32%**)
- 셀당 중앙값 27개, 최대 183개

**비균등 분포의 원인**: 알고리즘의 정규화 제약 조건에서 필연적으로 발생한다.

1. **Cx ≤ Dx** (x좌표 순 정렬) → Cx가 항상 작은 쪽으로 편향
2. **Cx + Dx ≤ 1** (대칭성 제거) → Cx ≤ 0.5로 제한되고, Dx는 중앙값이 0.5로 수렴
3. **A-B가 가장 먼 쌍** → C, D가 A-B 거리(√2) 이내로 제한, 4D 공간의 상당 부분이 기하학적으로 불가능

이 제약 조건은 좌표계 선택(A→(0,0), B→(1,1))과 무관하게 동일하게 적용된다. Astrometry.net은 이 분포 상태로 수백만 장의 사진을 성공적으로 처리하고 있으며, verification 단계에서 false match를 걸러내므로 실용적으로 문제가 되지 않는다.

### 접선 평면 투영

3D 단위벡터(천구 위의 점)를 2D 평면으로 변환하기 위해 접선 평면 투영(gnomonic projection)을 사용한다. 4개 별의 중심 방향에 접하는 평면에 투영하며, 이는 카메라의 핀홀 모델과 수학적으로 동일하다. 좁은 화각(수십 도 이내)에서 왜곡이 적어 해시 매칭이 잘 동작한다.

## 4. 런타임 매칭

브라우저에서 plate solving 시, 사진에서 검출한 별들로 quad를 생성하고 동일한 해시 계산을 수행한다. 이 해시를 KD-Tree에서 최근접 이웃(k=3) 검색하여 DB 후보를 찾는다.

### 성능 특성

| 단계 | 규모 | 비고 |
|:---|:---|:---|
| DB JSON 파싱 | 66 MB | 가장 큰 병목. 초기 로딩 시 1회 |
| KD-Tree 구축 | 546K 엔트리 | Web Worker에서 1회 |
| Quad 생성 (사진) | C(15, 4) = 1,365 | 상위 15개 별 사용 |
| KD-Tree 검색 | 1,365 x k=3 | 매우 빠름 (< 10ms) |
| Verification | 후보당 1,625별 투영 | 상위 20개 후보만 수행 |

## 5. 배포 최적화

### 현재 다운로드 리소스

웹에 호스팅하여 공개할 경우, 서버 비용 절감을 위해 클라이언트 사이드 컴퓨팅을 사용하되 다운로드 용량을 최소화해야 한다. 현재 주요 리소스 크기는 다음과 같다.

| 리소스 | 원본 크기 | gzip 전송 | 용도 |
|:---|:---:|:---:|:---|
| hashed-database.json | 66 MB | 22.5 MB | KD-Tree용 해시 DB |
| opencv.js | 11 MB | ~3 MB | 별 검출 (WASM) |
| vectors-database.json | 389 KB | 95 KB | 별 카탈로그 |
| vectors-constellations.json | 89 KB | 23 KB | 별자리 연결선 |
| 앱 번들 (Next.js) | ~수 MB | ~1 MB | 애플리케이션 코드 |
| **합계** | **~78 MB** | **~27 MB** | |

다운로드 용량의 대부분은 **hashed-database.json(22.5MB)**과 **opencv.js(~3MB)**가 차지한다.

### 최적화 방안

효과가 큰 순서대로 정리한다. 모든 방안은 매칭 정확도에 영향을 주지 않는다.

#### 1. 셀당 별 수 상한 도입 (66MB → ~10MB)

현재 셀 내 모든 별로 quad를 생성하지만, 사진 쪽에서는 상위 15개 밝은 별만 사용한다. DB 쪽에서도 셀당 밝은 별 상위 N개만으로 quad를 생성하면, 매칭 확률은 거의 동일하면서 DB 크기를 크게 줄일 수 있다.

| 셀당 상한 | 최대 quad/셀 | 예상 전체 quad | 예상 DB 크기 |
|:---:|:---:|:---:|:---:|
| 제한 없음 (현재) | 73,815 | 546K | 66 MB |
| 상위 20개 | 4,845 | ~150K | ~18 MB |
| 상위 15개 | 1,365 | ~80K | ~10 MB |

cell.ts에서 이미 밝기 순 정렬을 하고 있으므로, quad 생성 전에 `.slice(0, N)`을 추가하면 구현 가능하다. 단, 사진 쪽의 별 검출 밝기 순서가 카탈로그의 등급(V) 순서와 항상 일치하지는 않으므로(대기 조건, 카메라 감도 등), N은 사진 쪽(15)보다 약간 여유 있게 설정하는 것이 안전하다.

#### 2. OpenCV.js 제거 (11MB → 0)

현재 `cv.worker.js`의 `findStars()` 함수는 OpenCV를 다음 4개 연산에만 사용한다:

- `cv.cvtColor` — grayscale 변환
- `cv.GaussianBlur` — 가우시안 블러
- `cv.subtract` — 차영상 생성
- `cv.meanStdDev` — 평균/표준편차 계산

이 연산들은 모두 순수 JavaScript로 대체 가능하다:

- grayscale: Canvas API의 `getImageData`에서 RGB 가중 평균
- GaussianBlur: 분리 가능 커널(separable kernel)을 이용한 2-pass 블러
- subtract/meanStdDev: 단순 배열 연산

OpenCV.js(11MB WASM)를 완전히 제거하면 다운로드 용량이 크게 줄고, Web Worker의 초기화 시간도 단축된다.

#### 3. JSON → Binary 포맷 (추가 3~5x 축소)

hashed-database.json을 Float32Array 기반 binary 포맷으로 전환한다.

- 해시 값 4개(float32) + 별 ID 4개(uint16) = quad당 24바이트
- 80K quad 기준: 80,000 × 24 = 1.9MB (JSON 대비 ~5x 축소)
- JSON 파싱이 불필요해져 로딩 속도도 크게 향상
- gzip 압축 시 ~1MB 이하 가능

#### 4. KD-Tree 사전 직렬화

현재 매번 모든 엔트리를 KD-Tree에 삽입하여 구축한다. 사전 직렬화된 ArrayBuffer로 저장하면 구축 시간을 제거할 수 있다.

#### 5. 셀 크기 조정

nside를 높여 셀 수를 늘리면 셀당 별 수가 줄어 quad 폭발을 완화할 수 있다. 단, 셀이 작아지면 수집 반경도 함께 줄여야 하며, 경계 누락과의 균형이 필요하다.

### 최적화 효과 전망

| 단계 | 적용 후 gzip 전송량 | 비고 |
|:---|:---:|:---|
| 현재 | ~27 MB | |
| + 셀당 상한 (20개) | ~9 MB | DB 66MB → 18MB |
| + OpenCV.js 제거 | ~6 MB | 11MB WASM 제거 |
| + Binary 포맷 | ~3 MB | JSON 파싱 제거 |
| + 셀당 상한 (15개) | **~2 MB** | DB를 최소화 |

1~3번을 적용하면 현재 ~27MB에서 **~3MB**까지 줄일 수 있다. 이는 일반적인 웹 애플리케이션과 비슷한 수준이며, 모바일 환경에서도 부담 없는 크기이다.
