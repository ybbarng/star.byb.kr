# 점검 결과와 개선 계획

`docs/project-principles.md`의 원칙을 기준으로 제품을 점검한 결과와, 그에 따른 개선 목록이다.
항목을 해결할 때마다 상태를 바꾸고 결과(숫자)를 적는다.

## 진행 방향 (2026-10-19, 사용자 지시)

노이즈가 적은 사진으로 먼저 플레이트 솔버를 단단하게 만들고, 그다음 노이즈에 강건하게 만든다.
최종 목표는 노이즈가 많아도 강건한 방식이다.

1. **깨끗한 합성 사진**(카탈로그 좌표로 만든 가상 사진, `src/test/synthetic/`)으로 핵심 풀이를 확인한다
2. **노이즈를 단계적으로 늘린 합성 사진**(가짜 별, 위치 흔들림, 빠진 별, 넓은 화각)으로 강건하게 만든다
3. **실제 샘플 사진**으로 확인한다

## 1차 점검 (2026-10-19)

### 측정 방법
앱과 같은 흐름(자동 검출 → 가까운 중복 합치기 → 밝기 상위 100개 → Worker 풀이)을 Node에서
샘플 사진 16장 전체에 돌렸다. 브라우저에서도 북두칠성 샘플로 전체 흐름을 직접 확인했다.

### 발견한 문제

**① 틀린 해를 확신한다 (5번 원칙 위반, 가장 심각)**
- 노이즈 사진에서 거의 항상 "해 찾음"이 나온다. 정답을 아는 3장은 60~136° 빗나갔다.
- 원인: 지금 판정(`isPlausible`)의 유의도는 "inlier 수 ÷ 우연 기대치" 배수다. 그런데 풀이는 후보를
  수천~1만여 개 검사하고 그중 최댓값을 고른다. 기대치가 1개여도 1만 번 시도하면 8개쯤은 우연히 맞는다.
- 측정: "우연히 이만큼 맞을 확률" P(Poisson 꼬리)를 −log₁₀로 보면
  진짜 해는 **14~37**, 가짜 해는 **모두 3.9 이하**로 깨끗이 갈린다. 지금 유의도(배수)는 가짜가 46까지 나와 진짜(33~77)와 섞인다.

**② 느리다 (9번 원칙: 목표 10초)**
- 삼각형 인덱스 구축이 8.7초. 3단계에 들어갈 때마다 Worker를 새로 만들어 다시 구축한다.
- 해를 못 찾는 사진은 입력 크기 4가지(15/25/40/60개)를 모두 끝까지 돌아 3~12초, 최악 70초(오로라).
- 확신할 만한 해를 찾아도 나머지 입력 크기를 계속 돈다.

**③ 테스트가 앱의 실제 흐름을 지키지 못한다 (10·12번 원칙)**
- Worker의 풀이 흐름(입력 크기 여러 개, 후보 합치기, 어안 시도)이 Worker 파일 안에만 있어 Node에서 테스트할 수 없다.
- `big-dipper(북두칠성)를 정확히 푼다` 테스트는 결과를 출력만 하고 정답 여부를 확인하지 않는다.
  벤치마크 테스트들도 대부분 측정만 한다. 기존 동작이 깨져도 테스트가 통과한다.

**④ 검출 단계 UX**
- "흐릿"(주황) 표시가 북두칠성의 **가장 밝은 진짜 별**에 붙는다. 밝은 별은 원래 크게 번져 fwhm이 크기 때문이다.
- 디버그용 `console.log`(UUID, "별 수")가 남아 있다.
- Worker에서 오류가 나면 처리하지 않아 로딩 표시가 끝나지 않을 수 있다.

**⑤ 문서가 실제와 다르다**
- `CLAUDE.md`는 "4등급, 517개, ~1MB"라고 적혀 있지만 실제 DB는 V≤5, compact quad 84,962개, 10.8MB다.
